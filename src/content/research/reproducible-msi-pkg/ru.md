bitg — метод ввода: DLL, которую Windows загружает в каждое приложение, где вы печатаете. Это требует большого доверия, поэтому каждый релиз bitg выходит с подписанным build provenance, где указано, какой workflow собрал каждый файл и из какого коммита. Provenance говорит, кто собрал файл, но не позволяет проверить это утверждение самостоятельно. Воспроизводимая сборка позволяет: любой может собрать тот же коммит и сравнить хеши.

Пакеты `.deb` для Linux были воспроизводимыми уже в v0.3.1. MSI для Windows и `.pkg` для macOS — нет: две сборки одного коммита давали два разных файла. Эта статья о том, что именно различалось, слой за слоем, и о ловушках, в которые мы попали по пути. Работа вошла в PR #48 13 ноября 2026 года.

## Как мы искали

Метод был намеренно скучным: два git worktree одного коммита, один и тот же скрипт сборки в каждом, сравнение SHA-256, а при расхождении — переход на слой ниже. Проверки CI, которые теперь это охраняют, делают то же самое: создают на раннере второй worktree, собирают ещё раз и валят job при расхождении хешей, печатая хеши каждого бинарника, чтобы следующее различие было легко найти.

```steps
Бинарники :: Сначала сделать одинаковыми скомпилированные DLL и исполняемые файлы; иначе ничто выше них не будет стабильным.
Таблицы :: Сделать одинаковой базу установщика: коды продукта, код пакета, времена файлов.
Метаданные :: Зафиксировать summary information, которую инструмент установщика штампует текущим временем.
Контейнер :: Исправить временные метки в формате, который всё хранит: OLE для MSI и xar для .pkg.
Охрана :: Собирать дважды в CI при каждом значимом изменении и падать при любом различии.
```

Отправная точка в Windows — два MSI с хешами, начинающимися на `52E6606B` и `536D7B00`.

## Слой первый: бинарники

Бинарники Rust различались между worktree по трём причинам. В заголовке PE есть время линковки. В каталоге отладки есть GUID PDB и полный путь к файлу PDB. А сообщения panic и отладочная информация хранят абсолютные пути к исходникам, которые различаются, если worktree лежит в другой папке.

Линкер MSVC решает первые две проблемы флагами `/Brepro` (заменяет временную метку хешем результата) и `/PDBALTPATH:%_PDB%` (сохраняет только имя файла PDB). Оба попали в `.cargo/config.toml` для всех трёх целей Windows. Пути решает `--remap-path-prefix`: корень репозитория заменяется на `/build/bitg`, каталог cargo — на `/cargo`. Поскольку эти абсолютные пути известны только во время сборки, `installer/build.ps1` передаёт их в командной строке через `cargo --config`, а не коммитит.

После этого все четыре бинарника совпали, включая 32-битную DLL текстовой службы для старых приложений. MSI по-прежнему различались.

## Слой второй: WiX и что должен означать код продукта

Сравнение таблиц MSI показало три различия: ProductCode, PackageCode и даты. Если не сказать иначе, WiX при каждой сборке генерирует новые случайные ProductCode и PackageCode, а в cabinet записывает времена изменения файлов.

С временами файлов было просто: перед сборкой время изменения каждого устанавливаемого файла выставляется на время коммита (или на `SOURCE_DATE_EPOCH`, если задано). Код продукта потребовал больше размышлений, потому что это не просто число. По нему Windows Installer решает, является ли пакет новым продуктом, тем же продуктом или обновлением. Постоянный код был бы воспроизводимым, но неправильным: исправленная сборка той же версии выглядела бы идентичной старой.

Оба кода мы выводим как UUID на основе имени (версия 5): пространство имён — неизменный UpgradeCode установщика, а имя составлено из версии и SHA-256 каждого устанавливаемого файла и исходника WiX:

```text
seed        = "bitg-x64|<version>|" + sha256(each payload file, Package.wxs) joined by "|"
ProductCode = UUIDv5(UpgradeCode, seed + "|product")
PackageCode = UUIDv5(UpgradeCode, seed + "|package")
```

Одинаковые входные данные — одинаковые коды. Пересобранный бинарник той же версии получает новый код и устанавливается как обновление, что установщик уже разрешает. Файл проекта теперь отказывается собираться без ProductCode, поэтому MSI можно получить только через скрипт, который его вычисляет.

## Слой третий: поток summary и четыре байта

WiX записывает три важных здесь свойства summary information: PackageCode (свойство 9) и времена создания и последнего сохранения (12 и 13), которые он ставит в «сейчас». `build.ps1` открывает готовый MSI через COM-объект `WindowsInstaller.Installer`, записывает эти три свойства, сохраняет поток summary и коммитит базу.

Первая ловушка была банальной. `OpenDatabase` падал с `DISP_E_TYPEMISMATCH`, пока путь, полученный из `Join-Path`, не был явно приведён к `[string]` — вероятно, потому что иначе PowerShell передаёт в позднее связывание COM обёрнутый объект, а не простую строку.

Вторая ловушка оказалась интереснее. После всего перечисленного два MSI различались ровно в четырёх байтах, по смещению 8300. MSI — это составной файл OLE, маленькая файловая система внутри файла, и это смещение было временем изменения его корневой записи каталога. Ничто в нашем скрипте её не писало. Это делал `Commit`: сохранение базы штампует корневую запись контейнера текущим временем. Исправление, фиксирующее все остальные метки, само записывало свежую.

Поэтому после освобождения COM-объектов скрипт правит файл напрямую. Он читает из заголовка составного файла первый сектор каталога и размер сектора, находит корневую запись, проверяет, что её имя действительно `Root Entry`, и записывает время коммита как FILETIME по смещению 108 внутри этой записи. После этого оба worktree дали `13d83566…50ac`. В CI сквозной workflow дважды собрал MSI на раннере Windows и оба раза получил одинаковый хеш (`50d53ccb…37f4`, run 43315704109).

## .pkg: формат архива без настроек

В macOS понадобилась та же работа с бинарниками на своём диалекте: `--remap-path-prefix` для Rust, `-file-prefix-map` для Swift (иначе он встраивает пути `#file`), `ZERO_AR_DATE=1`, чтобы члены статических библиотек не несли дат, и `-Xlinker -S`, чтобы линкер не писал debug map с полным путём к статической библиотеке и именами временных объектных файлов. Перед запуском `pkgbuild` каждому файлу в папке подготовки пакета, включая скрипты установки, выставляется время коммита.

Этого не хватило из-за самого архива. `.pkg` — это архив xar: бинарный заголовок, сжатое zlib XML-оглавление (TOC), затем куча (heap) с данными файлов. `pkgbuild` записывает в оглавление время создания архива, ctime, mtime и atime внутренних файлов (Bom, Payload, Scripts, PackageInfo), а также пользователя, группу, номер устройства и inode того, кто собирал. Параметров, чтобы управлять этим, нет.

`tools/xar_normalize.py` переписывает эти поля задним числом: каждая метка времени становится временем коммита, владельцы — `root`/`wheel` с id 0, номера устройств — 0, а inode перенумеровываются по порядку, чтобы оставаться уникальными. Затем скрипт заново сжимает оглавление и пересчитывает его контрольную сумму — SHA-1 по смещению 0 в куче. Данные файлов и контрольные суммы отдельных файлов не трогаются. На подписанном архиве скрипт отказывается работать, потому что изменение оглавления сломало бы подпись. После нормализации сборка запускает `pkgutil --payload-files`, чтобы убедиться, что macOS по-прежнему читает пакет. Прежде чем доверять скрипту, мы проверили его на настоящем `.pkg` из релиза v0.3.1: новая контрольная сумма была верной, а куча не изменилась ни на байт. На более позднем push в `main` (run 43367788719) job macOS дважды собрал пакет и оба раза получил `ffd25c79…0e0c`.

## Ограничения

- **Только без подписи.** Гарантия распространяется на неподписанный MSI и `.pkg` с ad-hoc подписью. Подписи Authenticode и Developer ID добавляют свои временные метки и данные сертификата; для подписанного релиза нужен шаг «снять подпись, затем сравнить», который мы ещё не написали.
- **Одна машина, одинаковые инструменты.** Проверки CI собирают дважды на одном раннере. Это ловит метки времени и пути, но не различия между версиями компилятора, SDK или образами раннеров. Никто вне проекта пока не пересобирал релиз и не сравнивал результат.
- **Мы исправили форматы, которые нашли.** Смещение корневой записи CFB и поля xar обработаны потому, что на них указал diff. Новая версия WiX, `pkgbuild` или линкера может добавить поле, о котором мы не знаем. Проверка CI это поймает, но только после изменения.
- **Один путь сборки.** MSI теперь собирается только через `build.ps1`. Это сделано намеренно, но файл проекта сам по себе больше не пригоден.

Урок, который мы вынесли из четырёх байтов: фиксируя временные метки, проверьте, что записывает само сохранение.
