Узбекская клавиатура для трёх операционных систем

bitg переводит узбекские слова на алфавит 2026 года прямо во время набора — в Windows, Linux и macOS. Решение принимает одно ядро на Rust, а насколько трудно его применить, определяют три совершенно разные системы ввода.

  3. Linux: два фреймворка, одна общая оболочка

В октябре 2026 года Узбекистан принял закон, который заменяет четыре буквы латинского алфавита: oʻ становится ö, gʻ — ğ, sh — ş, ch — ç. На клавиатурах этих букв нет, а большинство пишущих по-узбекски каждый день пишут и по-английски, часто в одном и том же сообщении. Простая замена «найти и заменить» ломает check, shell и push.

bitg — наш ответ с открытым кодом: метод ввода, с которым вы продолжаете набирать o'zbek shahar, а при нажатии пробела текст превращается в özbek şahar — в любом приложении и без вмешательства в английский. 12 ноября 2026 года мы выпустили три релиза за один день: v0.1.0 для Windows (01:29 UTC), v0.2.0 с Linux (12:02 UTC) и v0.3.0 с бета-версией для macOS (14:23 UTC). Эта статья о том, чего стоило заставить один движок конвертации вести себя одинаково внутри трёх операционных систем, которые расходятся почти во всём.

Одно ядро, один маленький контракт

Все языковые решения находятся в bitg-core — крейте на Rust без зависимостей во время выполнения. Он разбивает текст на токены, определяет, узбекское ли слово (корпусный словарь, английский список SCOWL, списки брендов и иностранных имён, форма токена и контекст предложения), и применяет правила алфавита. Словари компилируются в бинарный файл, при запуске ничего не разбирается.

$ bitg "Menga chat yozing. Menga choy yozing."
Menga chat yozing. Menga çoy yozing.

Платформенные слои ничего не знают об узбекском языке. Они общаются с ядром через один вызов. Когда слово закончено, Session::complete_word возвращает Edit { delete, insert }, затрагивающий только это слово. Фаззинг-тест проверяет единственный инвариант, важный для безопасности: delete никогда не превышает длину только что набранного слова, поэтому ошибка в языковой логике не может «съесть» текст, написанный раньше.

Вся сложность проекта — в двух последних шагах, и в каждой системе она своя.

Windows: фреймворк работает, пока приложение не выходит из игры

В Windows bitg — текстовая служба Text Services Framework, написанная на Rust. Она не ставит клавиатурный хук. Изменения текста она отслеживает через ITfTextEditSink и заменяет законченное слово внутри edit session TSF. Это штатный и чистый путь: приложение видит обычное редактирование, его собственная история отмены не страдает.

Этот путь предполагает, что приложение открывает свой текст для TSF. Приложения на Qt, включая Telegram Desktop, этого не делают. Для них bitg переходит на запасной путь: восстанавливает слово по событиям клавиш и отправляет через SendInput нужное число Backspace и новое слово. До v0.1.0 понадобилось три отдельных исправления:

  • Наши собственные Backspace выглядели как пользовательские. bitg считает Backspace сразу после конвертации командой «отменить». В Qt нажатия, отправленные самим bitg, возвращались тем же путём, и он отменял собственную работу. Решение — счётчик повторного набора: bitg ждёт возвращения своих клавиш в окне 1,5 секунды и только потом снова слушает пользователя.
  • Люди печатают быстрее запасного пути. Клавиши, нажатые, пока исправление ещё стояло в очереди, попадали в его середину. Теперь bitg придерживает их и отправляет после правки в том порядке, в каком они были нажаты.
  • Qt теряет метку. Отправленные клавиши несут маркер в dwExtraInfo, чтобы служба могла их распознать. Qt это поле не передаёт, поэтому bitg узнаёт свои клавиши по порядку.

Сквозные тесты Windows на теге v0.1.0 прошли 59 проверок, включая окно PySide6, которое использует тот же путь ввода, что и Telegram. Стоит упомянуть ещё два более поздних исправления. В v0.3.1 bitg читает input scope поля (через ITfContext::GetAppProperty, с откатом на GetProperty для приложений, которые сообщают его так) и не работает в полях пароля, PIN и e-mail. А после сообщения о том, что в Windows 11 bitg сам переключался обратно на английскую раскладку, ошибка активации теперь записывается в лог, а не возвращается в TSF — именно из-за этого Windows отключала метод ввода. Так bitg остаётся выбранным, но это не объясняет, почему активация не удалась на той машине; issue по-прежнему открыт.

Linux: два фреймворка, одна общая оболочка

Для Linux мы вынесли логику набора из кода Windows в bitg-ime — платформенно-независимый крейт с C ABI. Поверх него работают тонкие оболочки: движок IBus на C и дополнение Fcitx5 на C++. Обе следуют одному правилу. Если приложение отдаёт текст вокруг курсора, слово заменяется на месте. Если не отдаёт или обещает отдать, но возвращает пустоту, слово удерживается как подчёркнутый текст preedit и фиксируется уже сконвертированным на границе слова. Если фокус уходит, preedit фиксируется без конвертации, и текст не теряется.

CI запускает настоящий ibus-daemon на Ubuntu 22.04 и печатает через него: восемь случаев — прямая конвертация, неизменный английский, кириллица, отмена через Backspace с обучением, Enter, preedit, сохранение preedit при смене фокуса и поле пароля. Сложнее всего оказался сам тестовый стенд. IBus.Bus.new() возвращает объект-одиночку на весь процесс, поэтому если создать его до появления сокета демона, тест навсегда остаётся без соединения; теперь стенд сначала ждёт сокет D-Bus.

Fcitx5 собирается, упаковывается и проверяется на линковку в CI, но в реальном приложении через него ещё никто не печатал, поэтому он выходит с пометкой «тестовый».

macOS: правильные смещения и меньше вопросов

В macOS оболочка — метод ввода InputMethodKit на Swift поверх того же C ABI bitg-ime, упакованный в один универсальный .pkg для Apple silicon и Intel.

Важными оказались две детали. Первая — единицы измерения: движок считает символы в скалярах Unicode, а диапазоны InputMethodKit — в UTF-16. Рядом с эмодзи они расходятся, поэтому сторона Swift пересчитывает длину удаления по самому тексту, прежде чем что-либо заменять.

Вторая — стоимость. Запрос текста перед курсором у приложения macOS — это межпроцессный вызов, и первая версия делала его на каждое нажатие. PR #9 добавил wants_before: движок сообщает оболочке, когда текст действительно нужен, — в начале слова, в конце и при отмене. Для слова choy с последующим пробелом число запросов упало с пяти до двух. Тест свойств прогоняет 600 случайных последовательностей клавиш против трёх видов приложений (отдающего текст, возвращающего пустой текст и не отдающего ничего) и проверяет, что результат совпадает с вариантом «спрашивать всегда». Чтобы убедиться, что тест это ловит, мы намеренно ломали wants_before двумя способами. Позже Linux перенял то же правило и ограничил запрос последними 128 символами.

Ограничения

  • macOS не проверена в реальных приложениях. CI запускает поддельное текстовое поле (13 случаев на момент появления беты) и устанавливает пакет на раннерах с Apple silicon и Intel. На этих раннерах без экрана выбор источника ввода возвращает ошибку -50, поэтому сквозной тест настоящего пути InputMethodKit там только компилируется; запускать его нужно вручную на Mac. Пока кто-нибудь не попечатает с ним в Safari, Chrome, Notes, Word и Telegram, версия для Mac остаётся бетой.
  • Fcitx5 не проверен в реальных приложениях, как сказано выше.
  • Поддержка Qt в Windows — запасной путь. Она восстанавливает слова по событиям клавиш, что по своей природе хрупче edit session TSF. Любое приложение, обрабатывающее клавиши необычным образом, может сломать её по-новому.
  • Клавиатуры для телефона пока нет. Мобильная клавиатура на том же ядре запланирована, но не выпущена.

Если бы мы начинали заново, мы сохранили бы именно эту границу. Ядро отвечает на один вопрос — «чем должно стать это слово», а каждая платформенная оболочка оценивается по тому, применяет ли она этот ответ, ничего больше не задевая.
